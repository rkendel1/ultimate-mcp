## Result

**9 of 9 tests pass**, against the real AuthBoundry server (built from `rkendel1/authboundry`
`0c982e4`) with real FeltDB persistence, through two independent MCP client implementations. The
suite was also checked for the ability to fail: two deliberately introduced defects (refusals not
recorded; a claimed principal header trusted) each made the client scenarios fail, the second at the
exact assertion "a claimed identity must never be attributed".

**Decision: the fallback architecture.** AuthBoundry is the only authority in a standalone gateway
built from `@appport/mcp` + `@appport/core` + `@feltdb/core`. **No FeltKit changes were made**; no
FeltKit branch exists.

## What M0.1 proves

1. An MCP caller is identified only by AuthBoundry: the gateway sends the application's check
   credential plus the caller's agent credential and **no principal id**; AuthBoundry derives the
   principal from its stored credential record on every call.
2. AuthBoundry decides every invocation; nothing executes without its exact allow for that
   application, capability and (when asked) delegator. A second check inside AppPort refuses any
   dispatch that did not come through such an allow.
3. Revoking a delegation, or an agent credential, stops the **next** call.
4. A request cannot choose its identity: headers, `_meta` and arguments claiming another principal are
   ignored or rejected; the work is attributed to the authenticated caller or refused.
5. Every attempted invocation leaves an append-only durable record: allowed, denied, unauthenticated,
   missing or malformed credential, unknown tool, authority unavailable, execution failure.
6. Evidence failure fails closed: no execution without its authorization on record; no reported
   success without its outcome on record; no refusal that disappears.
7. Records survive a SIGKILL of the gateway process, and FeltDB refuses to overwrite an existing record.
8. The official TypeScript SDK client (`@modelcontextprotocol/sdk` 1.32.2) and the official Python SDK
   client (`mcp` 2.3.0, a different protocol generation) observe identical authorization behaviour
   across 14 steps.

## What M0.1 does not prove

- **Not the application topology.** It proves a standalone gateway in its own process. It does not
  show a human application and an agent gateway sharing one authoritative state. FeltDB's local store
  has a single owner (`owner.lock`), and FeltKit cannot host another request handler; this remains an
  **unresolved integration constraint** (D7).
- **Not which software acted.** A valid agent credential proves that the caller held a credential
  bound to that principal. It does not establish which program, model or person held it.
- **Not the executing service's identity.** The gateway's identity in each record is asserted by its
  own configuration (`identity_basis: "asserted_by_configuration"`). AuthBoundry knows it only as the
  holder of the application's check credential.
- **Not hosted operation.** Local AuthBoundry (debug build) only; no hosted tenant, no shared host.
- **Not real agent clients.** Two SDK clients were used; no agent product (for example Claude Code)
  was run against it.
- **Not machine-crash durability.** Durability was shown across a process SIGKILL, not a power loss
  or disk failure.
- **Nothing about Build Sessions, the FeltKit application, compute or workspaces.**

## Identity, as recorded

| Identity | Record field | Basis |
|---|---|---|
| Authenticated caller | `caller.authenticated_principal_id`, `caller.authentication` | AuthBoundry authenticated the presented agent credential (possession of the credential) |
| Authorized principal | `authority.principal_id`, `authority.decision_id` | AuthBoundry's decision for that principal |
| Executing service | `executor.service`, `executor.identity_basis = "asserted_by_configuration"` | The gateway's own configuration |
| Claimed identities | not recorded as identity | Headers, `_meta`, arguments |

`authority.decision_id` is AuthBoundry's own id, or `null` whenever AuthBoundry recorded no decision
(credential rejected, authority unavailable, not asked). It is never invented.

## Evidence and fail-closed semantics

- Refused call: one `outcome` record (`status: refused`), committed, then the refusal is returned.
- Allowed call: an `authorized` record is committed **before** execution, then an `outcome` record
  (`completed` or `failed`) is committed **before** the result is returned.
- Evidence write fails before execution → `503`, nothing executes.
- Evidence write fails after execution → `503`, the result is withheld. The work did happen (it cannot be
  undone); the `authorized` record exists and its `outcome` is missing. **No automatic reconciliation
  exists yet**; finding authorized records without an outcome is a manual query today.
- Records hold no credentials (only AuthBoundry's credential id), no arguments (only a SHA-256 digest)
  and no results (only a reference such as `task:<id>`).

## Limitations (known, not hidden)

1. **Single-owner FeltDB** (D7): the gateway owns its store; nothing else can open it while it runs.
2. `initialize`, `ping` and `tools/list` need no credential; discovery shows every tool to anyone. Every
   call is decided when it is made. Per-caller tool lists are later work.
3. Refusals are MCP tool errors, not HTTP `401` with `WWW-Authenticate` as the MCP authorization
   specification describes for OAuth. Revisit with OAuth onboarding.
4. The delegator is named by an `x-boundry-on-behalf-of` header (validated by AuthBoundry, not trusted).
   Configuring it is client-specific.
5. Any principal granted `evidence.list` reads all of this application's evidence; there is no
   per-session or per-tenant evidence scoping yet.
6. No reconciliation of `authorized` records whose `outcome` was never written.
7. The AuthBoundry-timeout path is untested; only an unreachable AuthBoundry (connection refused) was
   exercised.
8. Agent credentials last at most 24 h, and the client must renew them; no MCP client does this
   automatically.
9. No CI: the suite needs a locally built AuthBoundry and the Python environment.
10. The gateway's check credential is read from an environment variable, not from a credential custody.
